# Skill: Update Docs

## Description
在每次 git push 成功后，自动更新架构说明（状态逻辑图.md）和工作日志（工作日志.md）。

## Trigger
- git push 成功完成后自动调用（由 git-push skill 的最后一步触发）
- 用户手动要求更新文档时

## 文件路径
- 架构说明：`状态逻辑图.md`（项目根目录）
- 工作日志：`工作日志.md`（项目根目录）

## Token 管理原则（必须遵守）

### 工作日志：只写不读
- **禁止**全文读取工作日志
- 如需了解上下文，只用 `tail -n 30 工作日志.md` 获取最近 30 行
- 追加时直接用 Edit 工具定位到文件末尾，不读全文

### 状态逻辑图：读全文，但控制体积
- 每次更新**只改相关章节**，不重写全文
- 文档总行数超过 300 行时，压缩历史备注、合并冗余说明
- 职责：描述**当前**系统状态，不是历史变更记录

---

## Steps

### 1. 获取本次变更信息（不读业务代码，只看 git）
```bash
git show HEAD --format="%H|%s|%ai" --no-patch   # commit 元信息
git diff HEAD~1 HEAD --stat                       # 改动文件列表
```

### 2. 判断是否需要更新状态逻辑图
**只有**本次 commit 改动了核心业务逻辑（状态机、数据模型、路由管道、核心流程）时才更新。
具体判断依据：查看 `git diff --stat` 的文件列表，如果涉及项目的核心逻辑文件则需要更新。

如需更新：
- 用 Read 工具读取状态逻辑图.md 全文（它是当前状态快照，必须读全）
- **只修改**与本次变更相关的章节，不动无关部分
- 图中描述要与 diff 内容一致

### 3. 追加工作日志（每次 push 必做）
**不要读取工作日志全文。** 直接在文件末尾追加：

```markdown
<改动的简短功能描述，2-4句话>

**存档点<7位hash>**
```

- 风格对齐文件现有风格（看 `tail -n 30 工作日志.md` 参考）
- commit 标题/hash 从步骤1的 git show 结果读取
- 不要加多余的 markdown 标题层级

### 4. 完成确认
输出：`文档已更新 ✓`

## Notes
- 工作日志体积会持续增长，这是设计上的预期——懒阅读即可，不要试图压缩它
- 状态逻辑图需要保持简洁可读，超长时主动压缩
- 如果工作日志.md 不存在，先创建再追加
